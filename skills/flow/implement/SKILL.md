# implement — 把一个单元做完

用户已经给了你**定义好的工作**（一条 issue、一张卡片、spec 里的某一项）。做完它，**不要扩张范围**。

1. **读清楚它。** 把正文里的验收条件逐条列出来；它引用的 PRD / SPEC / 设计文档一并读；再读相邻代码与现有测试，让命名、错误处理、日志风格与仓库一致。

2. **内联实现。** 就在当前会话里写代码——**不要**建 worktree、不要派子代理、不要建波分支：那些是 `/graph` 与 `/loop-it` 的编排，它们各自有自己的一套。需要先把行为定下来时用 `/test-first`（红 → 绿，一次一个接缝，接缝先与用户约定）。

3. **自证。** 跑**项目自己的门禁**（`mise run check`、`go build ./... && go test ./...`、`pnpm --dir web lint` …）：边写边跑相关单测，最后跑一次全量。补上验收条件隐含的测试——**没被测过的验收条件不算满足**。失败就先修，别把红的门禁留给下一步。

4. **收尾评审。** 用 `/review-it` 审这一份 diff（先定 Spec 轴：这条 issue 到底要求什么），改掉被接受的发现，再跑一次门禁。

5. **交付。** 用 `/ship-it`（commit → PR → 合入 → 关闭 issue）。需要留下设计决策、偏离、权衡时补 `/note-it`。

**在编排里运行时止于第 3 步。** 如果你是被 `/graph` 派出的一个节点，或者你是 `/loop-it` 正在处理的那一条 issue，那么这个技能到第 3 步（commit 到自己的分支）就结束了：**不要**执行第 4、5 步。评审与交付由编排器在波级 / 批末各做一次，节点自审和节点级 PR 都是这条路明确排除的。

**明确不做**：不 force-push、不替用户拍验收条件（含糊就先问清楚，别猜）、不把范围外的顺手改动塞进这份 diff（要改就另开一条）、不在没有门禁通过的情况下宣布完成。
