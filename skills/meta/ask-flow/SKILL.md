# ask-flow — 该用哪个技能

你想不起来 25 个技能各自管什么，所以问。

这是一个路由：说清你现在的处境（一个还没成形的想法、一堆进来的 issue、一段调不通的代码、一次漫长的实现），它给你该敲的下一步，以及那一步里哪些决定得你来拍。它只建议，不执行——不会替你 grill、写 spec、改文件，也不会顺手把你刚问到的那个技能跑起来。你自己敲下去，才说明你确认了那条路。

## 主线：想法 → 交付

大多数新功能走这条。

1. `/prd` — 把想法逼成需求文档。只有一个模糊念头就从这里开始；它会追问到"能写进验收条件"为止。
2. `/prd-to-spec` — 设计复杂时把 PRD 落成技术 SPEC（接口、数据、错误处理、契约）。简单改动跳过它：PRD 的验收条件已经够用，多写一份 SPEC 只会多一份要同步的东西。
3. `/to-issues` — 拆成垂直切片（每条都能单独演示）并写清真实的 blocking 边，创建到 GitHub 或本地。
4. 岔口：这批 issue 之间是什么关系？这一步选错，后面全是浪费。
   - 真并行（互不共享逻辑/文件）→ `/graph`：每节点独立 git worktree、按波 fan-out、波级一次集成一次评审一次交付。
   - 有依赖、基本串行，或干脆就是一条链 → `/loop-it`：一次一个、`.loop-state.json` 检查点、崩溃可恢复。
   - 只有一两个单元、共享文件，或只是链 → 都别用：走 `/implement`（内联实现 → 门禁自证 → `/review-it` → `/ship-it`）。上图和开循环在这三种情况下只会多付编排成本，而并行度并不会增加。
5. 执行（不管上面哪条）：实现 → 用项目自己的门禁自证 → 只 commit。节点/单个 issue 都不 push、不开 PR、不自审——评审要留给一个没写过这段代码的读者。
6. `/note-it` — 需要留下设计决策、偏离、权衡、待确认时用它；在交付前后都行。

## 岔路：从别的入口进来

- 有 bug、偶发 flake、性能回归 → `/diagnose`。它的纪律是：在有一条已经在「这个」bug 上变红的命令之前，不许开始推理；之后是最小化复现、写 3–5 条可证伪的假设、一次改一个变量地埋点、在正确的接缝上补回归测试。它不做 review/ship——定位清楚后按第 4 步回主线。
- 一堆别人提的 issue、原始 bug 报告 → `/triage`。它把外面的条目分流成 `ready` / `needs-info` / `bug-confirmed` / `duplicate` / `wontfix`，并把 `ready` 的补成 agent 可执行的卡片。`/to-issues` 产出的卡片不要 triage——那些已经 agent-ready。
- 想先把行为定下来再写实现 → `/test-first`：红 → 绿，一次一个接缝；`/implement` 内部就会用到它，也可以单独调用。
- 正在解 merge / rebase 冲突 → `/conflict`：查清两边意图后逐 hunk 解，跑项目门禁，永远解、不 `--abort`。它独立于所有流程。
- 从既有代码出发 → `/code-to-spec` 先把现状逆向成规格，再并回第 2 步之后的主线。

## 维护：不是新功能，只是让代码库保持可维护

- `/smell` — 找架构坏味道、复杂度热点、反模式（它是调查，不是修复）。
- `/refactor` — 按 Fowler 目录做不改行为的重构。
- `/modern-go` — Go 版本化的现代化改造（读 `go.mod` 决定规则集）。
- 三者是一条线：`/smell` 找到候选 → `/refactor` 或 `/modern-go` 动它。找到的"这里缺一个好的接缝"往往本身就是一个新 issue，可以并回主线。

## 理解与产出

- `/understand` — 把这次改动变成可交互的审阅网页（左树右 diff + 逐段解释），主要给人看。
- `/to-design` — Go 官方设计提案风格的设计文档（重"为什么"与权衡）。
- `/design-it` — 固定风格的 HTML 设计文档（目录、SVG 图、决策面板、测试用例）。
- `/insight-diagram` — UML / 架构图 / 流程图。

## 独立工具（模型不会主动挑它们）

`/humanize-it`（去 AI 味改写）、`/article-icons`（文章配图）、`/listenhub-tts`（文本转语音）。这三个只由人手敲触发——不进模型目录，你要它们时才敲。

## 最容易误用的七个边界

1. 链不要用 `/graph`。A→B→C 这种"每一步等上一步"的形态是链，用 `/loop-it`：`/graph` 的价值全部来自波内节点真独立，链只会把它退化成带额外仪式的串行。
2. 一个单元不要开循环。单点改动就是 `/implement`（内联 → 门禁 → `/review-it` → `/ship-it`），这也是技能里写着的默认。
3. 单节点波不建波分支。波里只有一个节点时没有可集成的东西，直接拿该节点分支评审与交付。
4. 节点不自审。节点的契约止于 commit；评审是波级一次（按节点分节过，重点看节点之间的结合部）。节点级 PR 是"昂贵模式"，用户明确要求才用。
5. 一批多 issue 共用一个 PR 时必须逐项列证据（commit / 关闭的 issue / 验证测试名 / 人工验收状态），否则 squash 之后无法单独回滚或审计。
6. 还没有会变红的命令时，不要开始猜假设。这是 `/diagnose` 存在的全部理由：先有环路，再有理论。
7. 不要 triage 自己拆出来的卡片。`/triage` 只管从外面进来的原始条目；`/to-issues` 的产物已经 agent-ready。

## 上下文卫生

"在哪个窗口里做"和"用哪个技能"同样重要：

| 情况 | 怎么做 |
| --- | --- |
| 一个单元、要在几轮里来回判断 | 内联做（`/implement`），不要开子代理 |
| 独立、自包含、你能把验收条件写清楚 | 派发一个**全新子代理**，一条自包含提示词 |
| ≥2 个真独立单元，且风险在集成处 | `/graph`：一波 2–3 个节点，波间有 fan-in 屏障 |
| 一串有依赖关系的 issue，要能崩溃恢复 | `/loop-it`，检查点落 `.loop-state.json` |

三条硬约束，违反了会静默出错：节点必须用绝对路径（子代理没有自己的 cwd，相对路径会改到编排者的检出）；共享检出必须始终干净（编排器据此做泄漏检查）；长构建/测试作为后台任务运行。节点停摆先用追加消息**让该子代理继续**（原地重试），再换新节点，再考虑剔除——它的兄弟节点本来就相互独立，不必陪等。

## 前置条件

流程假设三件事成立，否则门禁与泄漏检查都是空的：仓库有一个真实可跑的门禁命令（例如 `mise run check`）；工作树状态文件（`.graph_state`、`graph.html`、`.loop-state.json`、`nodes.json`）已进 `.gitignore`；`gh` 已登录（`/ship-it` 用它开 PR）。

## 维护规则

任何可被用户触达的技能被新增、改名或删除后，必须回来重读并更新这个路由——否则它会给出一条指向不存在技能的路线，而说谎的路由比没有路由更糟。同一件事还要同步到 `README.md` / `README_EN.md` 的技能表，以及 `docs/index_cn.html` / `docs/index_en.html` 的对应小节。
