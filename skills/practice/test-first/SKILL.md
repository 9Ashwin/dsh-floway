# test-first — 红 → 绿

TDD 就是 red → green 这个循环。这个技能是让循环产出**值得留下的测试**的参考：什么算好测试、测试写在哪、反模式、循环规则。**每一轮都适用——边写边看，不是事后补看。**

## 什么是好测试

测试通过**公开接口**验证**行为**，不碰实现细节。代码可以整个重写，测试不该跟着改。好测试读起来像规格说明："用户可以带有效购物车结账"直接告诉你存在什么能力，而且它熬得过重构，因为不关心内部结构。

## 接缝：测试写在哪里

**接缝**是你观察行为的公开边界。测试只写在接缝上，绝不写到内部。

**只测事先约定好的接缝。** 写任何测试之前，先把"要测哪些接缝"写下来并与用户确认。测不了所有东西；先约定接缝，测试精力才会落在关键路径和复杂逻辑上，而不是每个边界情况。先问：**公开接口是什么？我们该测哪几个接缝？**

接口本身的形状还在摇摆时（模块该多深、接缝该在哪、暴露什么），先把它定下来再写测试——用 `/to-design` 或 `/prd-to-spec` 把它写清楚。

## 三个反模式

- **与实现耦合**：mock 内部协作者、测私有方法、或从侧信道验证（绕开接口直接查数据库）。特征：重构时测试红了，但行为没变。
- **同义反复**：断言用与实现相同的方式重算期望值（`expect(add(a,b)).toBe(a+b)`、按同样逻辑手推的 snapshot、常量断言等于自身），于是它按构造就通过，永远不可能与代码意见相左。**期望值必须来自独立的事实来源**：已知good字面量、手算样例、规格。
- **横向切片**：先把所有测试写完再写实现。批量测试验证的是**想象出来的**行为——你测的是形状，不是面向用户的行为。改成**垂直切片**：一个测试 → 一段实现 → 再来一个；每个测试都是一颗**曳光弹**，回应上一轮学到的东西。

## 循环规则

- **红先于绿**：先写失败测试，再写刚好让它通过的最少代码。不预判后面的测试，不加投机功能。
- **一次一片**：一轮 = 一个接缝 + 一个测试 + 一个最小实现。
- **重构不属于这个循环**：它属于评审阶段（`/review-it`），不属于红绿实现循环。

## 在 DSH 里跑测试

每次 bash 调用都是**新 shell**，`cd` 不跨调用保留——用 `workdir=<目录>` 或 `cd <目录> && …`。长测试放后台任务。在 `/graph` 的节点里，路径必须是该节点 worktree 的**绝对路径**，否则你跑的是编排者的检出。收尾时按项目自己的门禁跑一次全量（`mise run check`、`go test ./...`、`pnpm --dir web test` …）。
